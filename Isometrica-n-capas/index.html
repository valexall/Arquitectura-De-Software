Guía de Arquitectura en N-Capas

Principios de Desacoplamiento, Responsabilidad Única y Correspondencia con el Proyecto UNAMBA

1. Jerarquía Estricta del Flujo de Información

En una arquitectura de N capas pura, la comunicación fluye **estrictamente de arriba hacia abajo para peticiones** y **de abajo hacia arriba para respuestas**. Ninguna capa puede saltarse a su vecina inmediata:

Capa 0: Clientes

Navegador, Postman, App Móvil. Emite JSON o formularios HTTP.

⬇ Petición HTTP / ⬆ Respuesta JSON
Capa 1: Presentación (Controlador)

Enrutamiento, deserialización y validación sintáctica. (rutas.py)

⬇ Llamada de Caso de Uso / ⬆ Entidades de Dominio
Capa 2: Negocio (Servicios)

Reglas de negocio, cálculos y validaciones. Si falla cupo ➔ Rechaza aquí sin tocar BD. (reservas.py)

⬇ Operación de Persistencia / ⬆ Registros Mapeados
Capa 3: Repositorio (DAL)

Abstracción de almacenamiento (Data Mapper). Aísla la BD del negocio. (memoria.py)

⬇ I/O de Bloques Físicos / ⬆ Tuplas Crudas
Capa 4: Base de Datos & Persistencia

Platos magnéticos, índices B-Tree, memoria y log WAL. (entidad.py / DB)

2. Las Tres Reglas de Oro de la Arquitectura

🚫 Prohibición de Saltos

El Controlador **NUNCA** debe saltarse el Servicio para llamar directamente al Repositorio o ejecutar SQL. Saltarse capas rompe la encapsulación de las reglas de negocio.

🛡️ Aislamiento del Dominio

La Capa de Negocio **NO DEBE** importar librerías web (como flask, request, jsonify). Debe poder probarse en segundos con tests unitarios puros.

🔄 Intercambiabilidad de Persistencia

El patrón Repositorio garantiza que podemos migrar de memoria volátil a PostgreSQL o MongoDB **sin cambiar ni una sola línea de la lógica de negocio**.
