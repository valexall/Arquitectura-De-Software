Semana 11 — Microservicio de facturación con Supabase

Guía de implementación, despliegue serverless, persistencia en PostgreSQL y consumo idempotente resiliente.

🎯 Resultado esperado

Un servicio independiente, desplegado por HTTPS, que recibe pedidos confirmados, conserva comprobantes internos en PostgreSQL y permite consultarlos sin duplicarlos al reintentar. Lo construyes en un repositorio nuevo. Después integras su API en tu aplicativo corregido de Semana 9, sin reemplazarlo.

⚠️ Alcance de demostración pedagógica

Es facturación de demostración: no cobra dinero, no emite comprobantes electrónicos SUNAT, no calcula IGV ni requiere datos personales. issued significa «comprobante interno generado»; no significa «pagado». En S09, confirmed significa stock asignado, no cobro realizado.

1. Lo relevante antes de empezar

Terminología clave para comprender el diseño arquitectónico, el código y la asistencia de IA:

Término Significado en esta práctica
Capacidad de negocio Algo que hace el negocio: aquí, emitir y consultar comprobantes. No separar servicios solo por tabla, lenguaje o capa técnica.
Microservicio Una capacidad con contrato y despliegue independientes y propiedad de sus datos. Tener otro repo o una URL no basta.
BaaS (Backend as a Service) Servicios de backend administrados: Supabase proporciona PostgreSQL, API de datos, Auth, Storage y ejecución de funciones. Nosotros elegimos cuáles usar.
Edge Function / serverless Código de servidor que Supabase ejecuta al recibir HTTP. Escribes la lógica sin administrar una máquina virtual. Sigue habiendo servidores, latencia y posibles fallos.
Endpoint Método + ruta, por ejemplo POST /invoices.
Contrato Reglas de entrada, autenticación, respuestas, errores e idempotencia que proveedor y consumidor deben respetar.
Snapshot Copia de los datos del pedido en ese momento. Cambiar el catálogo mañana no debe cambiar un comprobante ya emitido.
Autenticación / autorización Identificar al consumidor / decidir qué datos puede usar. Un token válido no debe dar acceso a las otras tiendas.
JWT / API key Un JWT contiene declaraciones firmadas; una API key acredita una aplicación. Las nuevas claves sb_publishable_... y sb_secret_... no son JWT. Nuestro token de facturación tampoco lo es [2].
RLS (Row Level Security) Reglas de PostgreSQL para limitar las filas a las que puede acceder un rol. No reemplaza los permisos de tabla ni la autorización del endpoint [3].
Idempotencia Repetir la misma operación no crea otro efecto. Aquí: una factura por (tienda, pedido), aunque lleguen reintentos simultáneos.
Timeout / retry Límite de espera / reintento de una operación transitoria. Un timeout no demuestra que el servidor no haya guardado la factura.

Cómo actúa Supabase como backend

Flujo de Arquitectura y Comunicación 
Navegador del aplicativo S09
        │
        ▼
Backend/worker S09 en tu PC        ← código del estudiante
        │ HTTPS + X-Billing-Token + JSON
        ▼
Supabase Edge Function: billing   ← nuestra lógica TypeScript/Deno
        │ supabase-js / API de datos PostgREST
        ▼
PostgreSQL: public.invoices        ← persistencia del servicio

La Edge Function autentica, valida, calcula el total y decide qué hacer ante duplicados. La API de datos traduce operaciones del cliente a consultas PostgreSQL. PostgreSQL guarda las facturas y hace cumplir la unicidad. Supabase administra esa infraestructura; no inventa las reglas de facturación por nosotros [1].

No necesitamos Supabase Auth, Storage ni Realtime para esta práctica. Tampoco un servidor FastAPI adicional dentro del nuevo repo: la Edge Function ya es nuestro backend HTTP. La tienda no obtiene acceso a tablas; obtiene acceso a una API acotada.

Propiedad de datos: S09 conserva pedidos y stock; facturación conserva comprobantes. Copiar un snapshot no es compartir una tabla. En esta práctica usas un proyecto Supabase propio para facturación. El patrón no exige necesariamente un servidor físico de base de datos por microservicio: también puede haber aislamiento lógico y permisos exclusivos [10].

Por qué usar RLS si ya tenemos un backend

Supabase puede exponer tablas de public mediante su Data API. Si solo proteges tu Edge Function pero dejas una tabla abierta, alguien podría intentar saltarse esa función y acceder por la API de datos [3].

Usaremos dos controles:

  1. Permisos de tabla: anon y authenticated no tienen permisos sobre invoices.
  2. RLS activado, sin políticas públicas: no concedemos acceso directo a filas desde clientes públicos.

La función usa una clave secreta interna, asociada a service_role, que omite RLS. Por eso cada lectura filtra issuer_id y cada inserción obtiene esa identidad del token, nunca del cuerpo enviado. RLS no separa las tiendas dentro de este cliente administrativo: la autorización de nuestra función lo hace [2][3].

Importante: No compartas claves sb_secret_..., service_role, la contraseña PostgreSQL ni tokens de administración. El compañero recibe solo un token propio de facturación. Ese token permite crear/consultar comprobantes de su tienda, no administrar Supabase.

2. Contrato que implementaremos

Dirección base del microservicio:

URL Base
https://TU_PROJECT_REF.supabase.co/functions/v1/billing

A esa base añades /health, /invoices o /invoices/ID. No dupliques /billing. TU_PROJECT_REF se reemplaza por la referencia real del proyecto, no por su nombre visible.

Método y ruta relativa Autenticación Resultado
GET /health No 200: el código responde. No comprueba la BD.
POST /invoices X-Billing-Token 201 si crea; 200 si recupera la misma factura.
GET /invoices/{id} X-Billing-Token 200 propia; 404 inexistente o de otra tienda.

Solicitud de emisión

HTTP Request POST /invoices 
POST /invoices
Content-Type: application/json
X-Billing-Token: TOKEN_DE_LA_TIENDA
Idempotency-Key: 11111111-1111-4111-8111-111111111111

{
  "order_id": "11111111-1111-4111-8111-111111111111",
  "currency": "PEN",
  "items": [
    {"product_id": "p1", "name": "Producto demo", "quantity": 2, "unit_price_cents": 2500}
  ],
  "total_cents": 5000
}

Reglas exactas del contrato:

  • Solo esos cuatro campos en el cuerpo y esos cuatro por línea. No envíes issuer_id, status, notification_status ni created_at.
  • order_id: UUID en minúsculas, conservando el ID del pedido S09. Idempotency-Key debe ser exactamente ese mismo ID. Es una regla de este servicio, no un estándar universal de HTTP.
  • currency: siempre PEN. Los importes son céntimos enteros, no soles ni strings. 2500 representa S/ 25.00.
  • Entre 1 y 6 líneas; productos distintos. product_id: 1–64 caracteres, letras/dígitos/guion/guion bajo; empieza con letra o dígito. name: texto no vacío, máximo 200 caracteres.
  • quantity: número entero de 1 a 5. Se rechazan true, "2" y fracciones. JSON no distingue semánticamente 2 de 2.0; ambos se parsean como el mismo número en JavaScript.
  • unit_price_cents: entero de 0 a 1 000 000 000. total_cents: entero igual a la suma de quantity × unit_price_cents. El servidor recalcula, no confía en el total recibido.
  • Máximo 32 768 bytes de cuerpo. No se aceptan campos extra.
  • Mismo consumidor + mismo pedido + mismo contenido normalizado: misma factura. Mismo pedido con otro nombre, precio o cantidad válida: 409. Ordenar de otra forma las claves JSON o las líneas no cambia la operación; cambiar el texto sí.
  • Otra tienda puede emitir su propio comprobante para un ID de pedido coincidente. La identidad se deriva de su token.

Respuesta de emisión y consulta

El cuerpo tiene id (UUID de la factura), number (DEMO- seguido del UUID completo), issuer_id, order_id, currency, items, total_cents, status: "issued" y created_at (fecha con zona horaria). Los genera o confirma el servidor; el consumidor no inventa el ID de factura. Las líneas se devuelven ordenadas por product_id.

El primer POST devuelve 201 y X-Idempotent-Replay: false; repetir devuelve 200 y X-Idempotent-Replay: true, con el mismo snapshot. Esto no cambia el contrato S09, cuyo POST de pedidos conserva sus propias reglas y códigos.

Todos los errores de la función siguen esta estructura canónica:

{"error":{"code":"IDEMPOTENCY_CONFLICT","message":"El pedido ya fue facturado con otro contenido."}}
HTTP Código Qué debe hacer el consumidor
400 BAD_JSON Corregir JSON.
401 UNAUTHORIZED Corregir token; no reintentar en bucle.
404 NOT_FOUND Revisar ruta, ID y consumidor.
405 METHOD_NOT_ALLOWED Usar el método indicado.
409 IDEMPOTENCY_CONFLICT Investigar el snapshot; no generar otro ID para evadirlo.
413 / 415 PAYLOAD_TOO_LARGE / UNSUPPORTED_MEDIA_TYPE Reducir cuerpo / usar application/json.
422 VALIDATION_ERROR Corregir campos, total o clave de idempotencia.
503 CONFIG_ERROR / DEPENDENCY_UNAVAILABLE Revisar configuración o reintentar un fallo transitorio con el mismo pedido y cuerpo.

El gateway puede devolver sus propios errores, por ejemplo 429 por límite o un 5xx. No supongas que todo error de red tendrá nuestro JSON.

3. Preparar el proyecto

Requisitos: cuenta y proyecto Supabase propio, Internet, Git, Node.js 20 o superior y Python 3. Comandos válidos en PowerShell, Bash o terminal de VS Code (en Windows python; en Linux python3).

4. Crear la tabla y cerrar el acceso directo

Crea la carpeta sql y el archivo sql/invoices.sql. Luego abre el SQL Editor del proyecto en Supabase, pega el bloque y ejecútalo:

sql/invoices.sql 
begin;
create table public.invoices (
  id uuid primary key default gen_random_uuid(),
  issuer_id text not null check (issuer_id ~ '^[a-z0-9_-]{1,40}$'),
  order_id uuid not null,
  currency text not null check (currency = 'PEN'),
  items jsonb not null check (jsonb_typeof(items) = 'array' and jsonb_array_length(items) between 1 and 6),
  total_cents bigint not null check (total_cents between 0 and 30000000000),
  status text not null default 'issued' check (status = 'issued'),
  request_hash text not null check (request_hash ~ '^[0-9a-f]{64}$'),
  created_at timestamptz not null default now(),
  constraint invoices_issuer_order_unique unique (issuer_id, order_id)
);
alter table public.invoices enable row level security;
revoke all on table public.invoices from PUBLIC, anon, authenticated, service_role;
grant select, insert on table public.invoices to service_role;
-- Sin políticas para anon/authenticated: esta tabla no es una API pública.
commit;

unique (issuer_id, order_id) lo hace cumplir PostgreSQL a nivel motor, incluso con peticiones simultáneas. No basta con «consulto si existe y luego inserto»: dos procesos concurrentes podrían consultar antes de que alguno inserte. request_hash permite verificar si el snapshot reenviado es idéntico. No usamos upsert para no sobrescribir facturas emitidas.

service_role necesita permisos explícitos además de omitir RLS: por eso el GRANT es explícito. No añadas políticas como USING (true) ni desactives RLS [3].

5. Crear credenciales distintas para dos consumidores

Crea crear_secretos.py en la raíz:

crear_secretos.py 
import json
from pathlib import Path
from secrets import token_hex

files = [Path(n) for n in ("billing.secrets.env", "cliente-propio.env", "cliente-par.env")]
if any(p.exists() for p in files):
    raise SystemExit("Ya existen archivos privados: no se sobrescribieron ni rotaron los tokens.")
clients = {"tienda-a": token_hex(32), "tienda-b": token_hex(32)}
files[0].write_text("BILLING_CLIENTS='" + json.dumps(clients, separators=(",", ":")) + "'\n", encoding="utf-8")
for file, issuer in zip(files[1:], clients):
    file.write_text("BILLING_TOKEN=" + clients[issuer] + "\n", encoding="utf-8")
for file in files:
    try:
        file.chmod(0o600)
    except OSError:
        pass
print("Creados billing.secrets.env, cliente-propio.env y cliente-par.env. No subir a Git.")

Ejecuta el script:

Terminal
python crear_secretos.py
Archivo generado Uso
billing.secrets.env Mapa secreto BILLING_CLIENTS: tienda-a → token A, tienda-b → token B. Se carga exclusivamente en Supabase.
cliente-propio.env Token de tienda-a para configurar tu propio backend S09.
cliente-par.env Token de tienda-b que compartirás en privado con tu compañero.
🔒 Manejo estricto de secretos

No compartas billing.secrets.env. Entrega a tu compañero únicamente el token de cliente-par.env por mensaje privado. Nunca lo publiques en URLs, READMEs, commits ni capturas de pantalla.

6. Implementar la Edge Function

Abre supabase/functions/billing/index.ts y sustituye todo su contenido por:

supabase/functions/billing/index.ts 
import { createClient } from "npm:@supabase/supabase-js@2.119.0";

type Item = { product_id: string; name: string; quantity: number; unit_price_cents: number };
type InvoiceInput = { order_id: string; currency: "PEN"; items: Item[]; total_cents: number };
const uuid = /^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/;
const columns = "id,issuer_id,order_id,currency,items,total_cents,status,created_at";
const maxBytes = 32_768;

class ApiError extends Error {
  constructor(public status: number, public code: string, message: string) { super(message); }
}
function fail(status: number, code: string, message: string): never {
  throw new ApiError(status, code, message);
}
function exact(value: unknown, keys: string[]): asserts value is Record<string, unknown> {
  if (!value || typeof value !== "object" || Array.isArray(value) ||
      Object.keys(value).length !== keys.length || !keys.every(k => Object.hasOwn(value, k))) {
    fail(422, "VALIDATION_ERROR", `Campos requeridos y únicos: ${keys.join(", ")}`);
  }
}
function validate(value: unknown): InvoiceInput {
  exact(value, ["order_id", "currency", "items", "total_cents"]);
  if (typeof value.order_id !== "string" || !uuid.test(value.order_id) || value.currency !== "PEN") {
    fail(422, "VALIDATION_ERROR", "order_id debe ser UUID en minúsculas y currency debe ser PEN.");
  }
  if (!Array.isArray(value.items) || value.items.length < 1 || value.items.length > 6) {
    fail(422, "VALIDATION_ERROR", "items debe contener entre 1 y 6 líneas.");
  }
  const seen = new Set<string>();
  const items: Item[] = value.items.map((item: unknown) => {
    exact(item, ["product_id", "name", "quantity", "unit_price_cents"]);
    if (typeof item.product_id !== "string" || !/^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$/.test(item.product_id) ||
        seen.has(item.product_id) || typeof item.name !== "string" ||
        item.name.length < 1 || item.name.length > 200 || !item.name.trim() ||
        typeof item.quantity !== "number" || !Number.isSafeInteger(item.quantity) ||
        item.quantity < 1 || item.quantity > 5 ||
        typeof item.unit_price_cents !== "number" || !Number.isSafeInteger(item.unit_price_cents) ||
        item.unit_price_cents < 0 || item.unit_price_cents > 1_000_000_000) {
      fail(422, "VALIDATION_ERROR", "Línea inválida, producto repetido o entero fuera de rango.");
    }
    seen.add(item.product_id);
    return { product_id: item.product_id, name: item.name,
      quantity: item.quantity, unit_price_cents: item.unit_price_cents };
  }).sort((a, b) => a.product_id < b.product_id ? -1 : a.product_id > b.product_id ? 1 : 0);
  const total = items.reduce((sum, i) => sum + i.quantity * i.unit_price_cents, 0);
  if (typeof value.total_cents !== "number" || !Number.isSafeInteger(value.total_cents) || value.total_cents !== total) {
    fail(422, "VALIDATION_ERROR", "total_cents debe ser entero e igual a la suma de las líneas.");
  }
  return { order_id: value.order_id, currency: "PEN", items, total_cents: total };
}
async function readJson(req: Request): Promise<unknown> {
  const reader = req.body?.getReader();
  if (!reader) fail(400, "BAD_JSON", "Falta el cuerpo JSON.");
  const chunks: Uint8Array[] = [];
  let size = 0;
  while (true) {
    const { value, done } = await reader.read();
    if (done) break;
    size += value.length;
    if (size > maxBytes) { await reader.cancel(); fail(413, "PAYLOAD_TOO_LARGE", "Máximo 32768 bytes."); }
    chunks.push(value);
  }
  const bytes = new Uint8Array(size);
  let offset = 0;
  for (const chunk of chunks) { bytes.set(chunk, offset); offset += chunk.length; }
  try { return JSON.parse(new TextDecoder().decode(bytes)); }
  catch { fail(400, "BAD_JSON", "JSON mal formado."); }
}
function issuerFor(req: Request): string {
  let clients: unknown;
  try { clients = JSON.parse(Deno.env.get("BILLING_CLIENTS") ?? "{}"); }
  catch { fail(503, "CONFIG_ERROR", "Configuración del servicio incompleta."); }
  if (!clients || typeof clients !== "object" || Array.isArray(clients)) {
    fail(503, "CONFIG_ERROR", "Configuración del servicio incompleta.");
  }
  const entries = Object.entries(clients);
  if (!entries.length || entries.some(([id, token]) => !/^[a-z0-9_-]{1,40}$/.test(id) ||
      typeof token !== "string" || !/^[0-9a-f]{64}$/.test(token)) ||
      new Set(entries.map(([, token]) => token)).size !== entries.length) {
    fail(503, "CONFIG_ERROR", "Configuración del servicio incompleta.");
  }
  const token = req.headers.get("X-Billing-Token") ?? "";
  const issuer = entries.find(([, expected]) => expected === token)?.[0];
  if (!issuer) fail(401, "UNAUTHORIZED", "Token ausente o inválido.");
  return issuer;
}
function database() {
  const url = Deno.env.get("SUPABASE_URL");
  const keys = JSON.parse(Deno.env.get("SUPABASE_SECRET_KEYS") ?? "{}");
  const key = keys.default ?? Deno.env.get("SUPABASE_SERVICE_ROLE_KEY");
  if (!url || !key) fail(503, "CONFIG_ERROR", "Faltan credenciales internas del servicio.");
  return createClient(url!, key, {
    auth: { persistSession: false, autoRefreshToken: false, detectSessionInUrl: false },
    global: { fetch: (input, init) => fetch(input, { ...init, signal: AbortSignal.timeout(5000) }) },
  });
}
function response(body: unknown, status = 200, headers: Record<string, string> = {}) {
  return Response.json(body, { status, headers: { "Cache-Control": "no-store", ...headers } });
}
function snapshot(row: Record<string, unknown>) {
  return { ...row, number: `DEMO-${row.id}` };
}

Deno.serve(async (req: Request) => {
  try {
    const path = new URL(req.url).pathname;
    if (req.method === "GET" && path === "/billing/health") {
      return response({ status: "ok", service: "billing", version: "1" });
    }
    const issuer = issuerFor(req);
    const match = path.match(/^\/billing\/invoices\/([0-9a-f-]{36})$/);
    if (req.method === "GET" && match && uuid.test(match[1])) {
      const { data, error } = await database().from("invoices").select(columns)
        .eq("issuer_id", issuer).eq("id", match[1]).maybeSingle();
      if (error) fail(503, "DEPENDENCY_UNAVAILABLE", "No se pudo consultar la factura.");
      if (!data) fail(404, "NOT_FOUND", "Factura no encontrada.");
      return response(snapshot(data));
    }
    if (path !== "/billing/invoices") fail(404, "NOT_FOUND", "Ruta no encontrada.");
    if (req.method !== "POST") return response({ error: { code: "METHOD_NOT_ALLOWED", message: "Usa POST." } }, 405, { Allow: "POST" });
    if ((req.headers.get("Content-Type") ?? "").split(";")[0].trim().toLowerCase() !== "application/json") {
      fail(415, "UNSUPPORTED_MEDIA_TYPE", "Usa Content-Type: application/json.");
    }
    const payload = validate(await readJson(req));
    if (req.headers.get("Idempotency-Key") !== payload.order_id) {
      fail(422, "VALIDATION_ERROR", "Idempotency-Key debe ser exactamente order_id.");
    }
    const hash = Array.from(new Uint8Array(await crypto.subtle.digest("SHA-256",
      new TextEncoder().encode(JSON.stringify(payload))))).map(b => b.toString(16).padStart(2, "0")).join("");
    const db = database();
    const { data, error } = await db.from("invoices").insert({
      ...payload, issuer_id: issuer, request_hash: hash,
    }).select(columns).single();
    if (!error) return response(snapshot(data), 201, { "X-Idempotent-Replay": "false" });
    if (error.code !== "23505") fail(503, "DEPENDENCY_UNAVAILABLE", "No se pudo guardar la factura.");
    const existing = await db.from("invoices").select(`${columns},request_hash`)
      .eq("issuer_id", issuer).eq("order_id", payload.order_id).single();
    if (existing.error) fail(503, "DEPENDENCY_UNAVAILABLE", "Reintenta con la misma clave y cuerpo.");
    const { request_hash, ...row } = existing.data;
    if (request_hash !== hash) fail(409, "IDEMPOTENCY_CONFLICT", "El pedido ya fue facturado con otro contenido.");
    return response(snapshot(row), 200, { "X-Idempotent-Replay": "true" });
  } catch (error) {
    if (error instanceof ApiError) return response({ error: { code: error.code, message: error.message } }, error.status);
    console.error("billing: fallo interno; no se registran tokens ni cuerpos");
    return response({ error: { code: "DEPENDENCY_UNAVAILABLE", message: "Servicio temporalmente no disponible." } }, 503);
  }
});

Configuración de la función en supabase/config.toml:

supabase/config.toml
[functions.billing]
enabled = true
verify_jwt = false
entrypoint = "./functions/billing/index.ts"

¿Por qué verify_jwt = false? Nuestros consumidores no envían un JWT de Supabase Auth: envían un token propio en X-Billing-Token. La función los autentica internamente en issuerFor(). Desactivar esta comprobación del gateway solo es correcto porque implementamos autenticación personalizada [4].

Reemplaza TU_PROJECT_REF en cada comando. --use-api realiza el empaquetado y build en los servidores de Supabase, evitando instalar Docker o Deno en tu máquina. Verifica en Edge Functions → billing del Dashboard que el servicio está activo.

8. Probar el servicio antes de tocar S09

8.1 Primera emisión manual

  1. GET BASE/health: Espera 200 con {"status":"ok","service":"billing","version":"1"}.
  2. POST BASE/invoices con el JSON de la sección 2 y tu token de cliente-propio.env (sin BILLING_TOKEN=). Espera 201 y guarda el id.
  3. Repite exactamente el mismo POST: espera 200, X-Idempotent-Replay: true y el mismo comprobante.
  4. GET BASE/invoices/ID_RECIBIDO: comprueba la lectura.
  5. Verifica la fila en el Table Editor de Supabase.

8.2 Comprobador HTTP reproducible

Crea probar_billing.py en la raíz:

probar_billing.py 
"""Prueba el contrato por HTTP; no necesita librerías ni claves de Supabase."""
import copy
import getpass
import json
import os
import uuid
from concurrent.futures import ThreadPoolExecutor
from urllib.error import HTTPError
from urllib.request import Request, urlopen

base = (os.getenv("BILLING_BASE_URL") or input("URL base terminada en /functions/v1/billing: ")).rstrip("/")
token_a = os.getenv("BILLING_TOKEN") or getpass.getpass("Token de tienda-a: ")
token_b = os.getenv("BILLING_PEER_TOKEN") or getpass.getpass("Token de tienda-b: ")
assert base.startswith("https://") or base.startswith("http://127.0.0.1:"), "Usa HTTPS; HTTP solo para prueba local."
assert token_a != token_b, "Usa dos tokens distintos."
passed = []

def call(method, path, body=None, token=token_a, key=None, raw=None, content_type="application/json"):
    headers = {"Content-Type": content_type}
    if token:
        headers["X-Billing-Token"] = token
    if key is not None:
        headers["Idempotency-Key"] = key
    data = raw if raw is not None else (json.dumps(body).encode() if body is not None else None)
    req = Request(base + path, data=data, headers=headers, method=method)
    try:
        result = urlopen(req, timeout=20)
    except HTTPError as error:
        result = error
    with result:
        return result.status, json.loads(result.read())

def check(label, condition):
    assert condition, "FALLÓ: " + label
    passed.append(label)
    print("PASA:", label)

order = {"order_id": str(uuid.uuid4()), "currency": "PEN", "items": [
    {"product_id": "p2", "name": "Cable demo", "quantity": 1, "unit_price_cents": 1000},
    {"product_id": "p1", "name": "Producto demo", "quantity": 2, "unit_price_cents": 2500}], "total_cents": 6000}
key = order["order_id"]
check("health (no prueba la BD)", call("GET", "/health", token="")[0] == 200)
check("sin token", call("POST", "/invoices", order, token="", key=key)[0] == 401)
status, invoice = call("POST", "/invoices", order, key=key)
check("crear factura persistida", status == 201 and invoice["total_cents"] == 6000 and invoice["issuer_id"] == "tienda-a")
status, repeated = call("POST", "/invoices", order, key=key)
check("reintento sin duplicar ni cambiar snapshot", status == 200 and repeated == invoice)
status, read = call("GET", "/invoices/" + invoice["id"])
check("consulta persistida", status == 200 and read == invoice)
changed = copy.deepcopy(order)
changed["items"][0]["name"] = "Otro nombre"
status, error = call("POST", "/invoices", changed, key=key)
check("conflicto con cuerpo diferente", status == 409 and error["error"]["code"] == "IDEMPOTENCY_CONFLICT")
for label, change in [
    ("rechaza booleano como cantidad", lambda x: x["items"][0].update(quantity=True)),
    ("rechaza string como cantidad", lambda x: x["items"][0].update(quantity="1")),
    ("rechaza total alterado", lambda x: x.update(total_cents=1)),
    ("rechaza issuer enviado en cuerpo", lambda x: x.update(issuer_id="tienda-b")),
]:
    invalid = copy.deepcopy(order)
    change(invalid)
    check(label, call("POST", "/invoices", invalid, key=key)[0] == 422)
check("exige clave igual al order_id", call("POST", "/invoices", order, key="otra-clave")[0] == 422)
check("no revela factura de otra tienda", call("GET", "/invoices/" + invoice["id"], token=token_b)[0] == 404)
status, peer = call("POST", "/invoices", order, token=token_b, key=key)
check("aísla mismo order_id entre tiendas", status == 201 and peer["id"] != invoice["id"] and peer["issuer_id"] == "tienda-b")
reordered = copy.deepcopy(order)
reordered["items"].reverse()
check("orden de líneas no cambia operación", call("POST", "/invoices", reordered, key=key) == (200, invoice))
concurrent = copy.deepcopy(order)
concurrent["order_id"] = str(uuid.uuid4())
with ThreadPoolExecutor(max_workers=5) as pool:
    results = list(pool.map(lambda _: call("POST", "/invoices", concurrent, key=concurrent["order_id"]), range(5)))
check("5 llamadas simultáneas producen una sola factura", sorted(s for s, _ in results) == [200, 200, 200, 200, 201] and len({r["id"] for _, r in results}) == 1)
check("JSON mal formado", call("POST", "/invoices", raw=b"{", key=key)[0] == 400)
check("Content-Type incorrecto", call("POST", "/invoices", order, key=key, content_type="text/plain")[0] == 415)
check("limita tamaño del cuerpo", call("POST", "/invoices", raw=b" " * 32769, key=key)[0] == 413)
print(f"\n{len(passed)}/{len(passed)} pruebas superadas. Estas pruebas crean 3 facturas sintéticas por ejecución.")

Ejecuta: python probar_billing.py e ingresa la URL y los dos tokens.

9.1 Transformación exacta del contrato S09

Campo Facturación De dónde sale en S09

currency "PEN", moneda fija de la campaña S09.

items[].name order.items[].name
items[].quantity order.items[].quantity
items[].unit_price_cents order.items[].unit_price_cents

9.2 Configuración, flujo y errores

Variables a configurar en el entorno de S09 (ignoradas por Git):

BILLING_BASE_URL=https://TU_PROJECT_REF.supabase.co/functions/v1/billing
BILLING_TOKEN=TOKEN_ASIGNADO_A_ESTA_TIENDA

En Docker Compose, pásalas en el bloque environment compartido por api y worker:

    BILLING_BASE_URL: ${BILLING_BASE_URL:-}
    BILLING_TOKEN: ${BILLING_TOKEN:-}

Aplica cambios recreando los contenedores:

docker compose up -d --force-recreate api worker

Flujo esperado del ciclo de vida:

  1. Pedido confirmado y persistido en S09.
  2. Tarea de facturación con snapshot inmutable.
  3. POST HTTPS al microservicio de facturación.
  4. Guardar relación pedido ↔ factura o estado de fallo pending.
  5. Mostrar al usuario comprobante / facturación pendiente.
🛡️ Principios de desacoplamiento
  • No metas la llamada remota dentro de una transacción de stock ni vuelvas a crear el pedido para facturarlo.
  • El fallo de facturación no revierte una venta confirmada.
  • No elimines el consumidor de notificaciones ya existente para reemplazarlo por facturación.
  • Añade tu propio estado local de facturación (ej: pending → issued / failed). No lo confundas con notification_status.
  • Usa timeout finito (ej. 15 segundos).

9.3 Resiliencia básica que debe verse funcionando

Implementa timeout + idempotencia + recuperación mediante reintento manual. Un timeout puede ocurrir tras guardar en Supabase; el reintento recupera la misma factura sin duplicarla.

10. Validación entre dos compañeros

  1. A comprueba su propio servicio con el script y su S09 local.
  2. A comparte con B la URL HTTPS base y únicamente el token de tienda-b (de cliente-par.env). No comparte claves de BD ni token propio.
  3. En su S09 local, B configura el servicio de A con ese token. B confirma un pedido propio, emite comprobante y lo consulta.
  4. B repite la solicitud para el mismo pedido: debe devolver el mismo comprobante (200), no crear otra fila.
  5. A intenta consultar con su token A el comprobante generado por B: debe recibir un 404 (aislamiento multitenant).
  6. Invertir roles: ahora B provee y A consume.

12. Errores frecuentes

Síntoma Revisión concreta
401 antes de ejecutar el handler Revisa verify_jwt = false en supabase/config.toml, despliega otra vez y confirma el proyecto.
Nuestro UNAUTHORIZED (401) Se ejecutó el código: revisa cabecera X-Billing-Token, token sin espacios/prefijo y mapa cargado en ese mismo proveedor.
503 CONFIG_ERROR BILLING_CLIENTS vacío/JSON incorrecto, tokens repetidos o que no tienen 64 caracteres hex, o faltan credenciales internas.
503 DEPENDENCY_UNAVAILABLE Revisa tabla, permisos, proyecto, disponibilidad y logs de la función. No publiques tokens ni el cuerpo completo al depurar.
404 NOT_FOUND Base incorrecta, /billing duplicado en la ruta, ID de pedido usado como ID de factura, o token de otra tienda.
422 VALIDATION_ERROR Cuerpo del checkout en lugar de snapshot persistido, campos extra, total incorrecto o Idempotency-Key distinto al UUID del pedido.
Error CORS desde el navegador Llamada realizada desde el cliente. La integración es backend → backend; no agregues * ni expongas el token en frontend.
CLI intenta cambiar destino erróneo Esta guía usa CLI 3.0.0 y --remote=REF. Revisa versión y destino; no ejecutes comandos v2.
/health responde pero facturar falla La salud de proceso no comprueba PostgreSQL: ejecuta POST, GET y verifica fila en base de datos.
S09 indica que falta configurar facturación Revisa BILLING_TOKEN dentro del contenedor en ejecución. Añádelo a environment y recrea api y worker con --force-recreate.
